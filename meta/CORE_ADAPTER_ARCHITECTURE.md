# 코어-어댑터 아키텍처 (Core-Adapter Architecture)

> **메타 원칙 SSoT**: 본 문서는 `prompt_agent`의 프롬프트 파일 구조 기준이다.
> 이 아키텍처는 [DESIGN_PRINCIPLES.md](DESIGN_PRINCIPLES.md) 원칙 5(구동 환경 최적화)를 NotebookLM 특화에서 **환경 중립**으로 일반화한 것이며, [KNOWLEDGE_SYSTEM.md](KNOWLEDGE_SYSTEM.md)의 특화 전략(매체별 sub-prompt)과 직교한다.
> 결정 경위: [journal/DIALOGUE.md](../journal/DIALOGUE.md) [2026-05-28]

---

## 1. 왜 분리하는가

프롬프트를 **환경 중립 코어**(행위 정의)와 **환경별 어댑터**(실행 인터페이스)로 분리한다.

연구자가 여러 AI(NotebookLM·Claude·Codex 등)를 병행하므로 "1순위 환경"을 정하는 프레임 자체가 맞지 않다. 같은 *행위*를 환경만 바꿔 재현할 수 있어야 하며, 그래야 추후 스킬화 시 코어를 재료로 쓸 수 있다.

**핵심 구분**: 코어는 **무엇을**(what) 하는가, 어댑터는 그 환경에서 **어떻게**(how) 실행·표기하는가.

### 매체(Medium) vs 환경(Environment) — 두 축의 분리

분리 작업에서 혼동을 막기 위해 두 축을 구별한다.

- **매체**: 소스 자체의 성격 (영상 / 논문 / 법령 / 기사…). → KNOWLEDGE_SYSTEM의 **특화 전략**이 담당. 매체 차이는 **코어 안에서** sub-prompt로 흡수한다 (RES-002-A 논문 / RES-002-G 영상).
- **환경**: 프롬프트를 실행하는 도구 (NotebookLM / Claude.ai / Claude Code / Codex…). → **본 아키텍처**가 담당. 환경 차이는 **어댑터로** 흡수한다.

> 즉 "영상의 filler·광고 제거"는 *매체* 특성이므로 코어, "NotebookLM 체크박스에서 소스 선택"은 *환경* 특성이므로 어댑터다.

## 2. 2층 분해(Atom / Composite)와의 관계

| 층 | 정의 | 코어/어댑터 |
|----|------|------------|
| **Atom** | 여러 프롬프트에서 호출 가능한 재사용 최소 단위 (예: 글로사리 추출, 인용 검증) | 코어로 작성. 어댑터는 보통 불필요(Composite의 어댑터가 흡수) |
| **Composite** | 한 호흡에 완결되는 업무 단위 (예: 영상 1편 해체) | 코어 + 환경별 어댑터 |

Atom과 Composite 모두 **코어**는 환경 중립이다. 어댑터는 실제 사용자가 실행하는 단위인 **Composite**에 붙는 것을 기본으로 한다.

## 3. 코어 파일 스키마

코어는 환경·실행 UI에 대한 언급을 일절 포함하지 않는다. 포함 섹션:

| 섹션 | 내용 | 비고 |
|------|------|------|
| 헤더 메타 | ID · 제목 · 부제 · 버전 · 층(Atom/Composite) · 매체 · AI 역할(F/CF/전환) · 도메인 | |
| 목표 행위 | 입력→출력, 어떤 판단의 비용을 낮추는가 | DESIGN 원칙 1 |
| 위임 가능 범위 | 가용성 / 주도권 | DESIGN 원칙 2 |
| AI 역할 | Facilitator / Critical Friend / 전환 트리거 | DESIGN 원칙 3 |
| (해당 시) 모드 정의 | deep/brief/recipe 등 분기 정의 | |
| 절차 | Step 0~N | DESIGN 원칙 4 (구조) |
| 출력 형식 | 섹션 구조와 항목. 출처가 필요한 자리에 **환경 중립 출처 플레이스홀더**(`[출처]` / `[시점]` / `[출처+시점]`)를 둔다. 실제 마커 형식은 어댑터가 치환 | §5, 부록 A |
| 제약조건 | **행위 원칙만**. 환각 금지는 코어, "선택된 소스" 같은 UI 어휘는 제외 | |
| 입력 변수 명세 | 슬롯을 *선언*만 (예: `INPUTS: mode | annotation | research_context | focus`). 전달 방식 안내는 어댑터 | |

## 4. 어댑터 파일 스키마

어댑터는 코어가 비워둔 환경 인터페이스만 채운다. 포함 섹션:

| 섹션 | 내용 |
|------|------|
| 어댑터 헤더 | 짝이 되는 코어 ID + 대상 환경 (예: `RES-002-G` × `notebooklm`) |
| 실행 전 준비 | 환경별 소스 투입 방법 (NotebookLM 체크박스 선택 / Claude.ai 첨부 / CC 파일 경로 등) |
| 인용·참조 규약 (횡단) | 코어의 출처 플레이스홀더(`[출처]` / `[시점]` / `[출처+시점]`)를 환경별 실제 형식으로 치환하는 규칙 표. (예: NotebookLM `[출처]`→`[1]`, `[출처+시점]`→`[1] mm:ss`) + "모든 토큰을 빠짐없이 채우라"는 강제 |
| 입력 전달 방식 | 코어가 선언한 입력 슬롯을 사용자에게 어떻게 보여주고 채우게 할지 |
| 환경 특화 제약 | 해당 환경에서만 필요한 추가 제약 (예: NotebookLM 환각 차단 강조) |
| 조립 안내 | 코어와 합치는 순서 (§6 워크플로 참조) |

## 5. 경계선 판정 트리

새 프롬프트나 기존 프롬프트의 한 항목이 코어인지 어댑터인지 헷갈릴 때 적용한다.

```
Q1. 이 항목이 빠지면 행위 자체가 작동하지 않는가?
    YES → 🟢 코어
    NO  → Q2

Q2. 이 항목이 NotebookLM 외 환경에서 다른 표현·다른 UI로 바뀌어야 하는가?
    YES → 🔴 어댑터
    NO  → 제거 후보 (둘 다 필요 없음)

Q3. Q1과 Q2가 모두 YES인가? (= 의미는 코어, 표현은 환경별)
    YES → 🟡 분할: 의미적 본질을 코어, 표기·UI 형태를 어댑터로 쪼갠다
```

🟡 분할 패턴의 전형: 인용 마커(의미=출처 추적은 코어, **출처 토큰으로 자리만 남김** / 형식=`[1]`은 어댑터가 치환), 입력란(변수=코어 / "복사해서 채우세요" 안내=어댑터).

> **출처 토큰 규약** (부록 A 파일럿에서 확정): 코어는 출처가 필요한 자리에 `[출처]`(참조만) · `[시점]`(시간 좌표만) · `[출처+시점]`(둘 다) 세 토큰을 둔다. *어느 자리에 시간 좌표가 필요한가*는 매체 특성이라 코어 소관이고, 그 토큰을 `[1]`·`mm:ss` 같은 실제 마커로 바꾸는 형식은 환경 특성이라 어댑터 소관이다.

## 6. 합본 빌드 & 실행 워크플로

조립은 **빌드 스크립트로 자동화**한다 (수동 복붙에서 승격 — NotebookLM 채팅 입력 한도 때문에 합본을 미리 만들어 두는 게 필요해졌다).

```
1. core/ 와 adapters/ 의 짝 파일을 편집한다 (이것이 원본 = SSoT).
2. build_notebooklm.ps1 실행 → notebooklm/ 에 정제된 합본 자동 생성.
3. notebooklm/{파일}.notebooklm.md 내용을 복사해 NotebookLM 채팅에 붙여넣는다.
4. 대상 소스(영상 등)를 선택한 상태로 실행한다.
```

- **합본은 파생물**: core/ 또는 adapters/를 고치면 스크립트를 재실행해 합본을 갱신한다 (drift 방지). 합본을 직접 편집하지 마라.
- **빌드 시 자동 정제**: 작성용 메타(HTML 주석·`>` 안내·`[필수]`/`[선택]` 태그·메타 헤더 표·버전 푸터)는 합본에서 자동 제거되어, 채팅 입력 한도를 아낀다.

### 입력 길이도 어댑터의 책무다 (파일럿 발견)
NotebookLM 채팅은 입력 한도가 빡빡하다(코어 1개도 초과 가능). 어댑터/빌드는 인용 형식뿐 아니라 **그 환경의 입력 길이 제약과 전달 방법**까지 흡수해야 한다. 길이가 한도를 넘으면 파이프라인 분할(예: 모드 판별기 → 모드별 프롬프트)로 쪼갠다.

## 7. 명명·디렉토리 규칙

```
prompts/
├── atoms/                              # Atom (도메인 횡단 재사용 최소 단위)
│   └── ATOM-{slug}.md
├── research/                           # 연구 도메인
│   ├── core/                           # 코어 (환경 중립) — 전환 완료된 것
│   │   └── {코어파일명}.md
│   ├── adapters/                       # 어댑터
│   │   └── {코어파일명}.{환경}.md
│   ├── notebooklm/                     # 빌드 산출물 (NotebookLM 합본, 파생물)
│   │   └── {코어파일명}.notebooklm.md
│   ├── build_notebooklm.ps1            # 합본 빌드 스크립트
│   └── RES-000~004*.md                 # (직속) 미전환 레거시
└── personal/
```

- **어댑터 파일명**: `{코어파일명}.{환경슬러그}.md` — 코어와 **동일 베이스명**(빌드 스크립트가 짝을 이 이름으로 매칭).
- **환경 슬러그**: `notebooklm` · `claude-chat` · `claude-code` · `codex` · `gemini` · `antigravity`
- **합본**(`notebooklm/` 등 환경명 폴더): `build_notebooklm.ps1`이 `core/`+`adapters/`에서 생성하는 **파생물**. 직접 수정 금지 — 원본을 고치고 스크립트를 재실행해 갱신한다.
- **위치 = 상태**: `core/`에 있으면 코어-어댑터 전환 완료, research/ 직속에 있으면 미전환 레거시.

## 8. 버전 규칙

코어-어댑터 구조는 새로운 빌딩블록 체계다. 버전은 이 체계 기준으로 매긴다.

- **전환 시 v1.0으로 리셋**: 기존 단일 프롬프트(예: 영상 v2.0)를 코어-어댑터로 전환하면, 코어의 버전은 **v1.0에서 새로 시작**한다. 이전 버전 숫자를 이어받지 않는다.
- **계보 보존**: 대신 코어 헤더에 `계보` 행을 두어 전신 버전을 한 줄로 남긴다 (예: "전신: 영상 v2.0 멀티모드"). 이력은 보존하되 버전 숫자는 리셋.
- **코어와 어댑터는 독립 버전**: 코어가 바뀌면 코어만 v1.1·v2.0…, 어댑터가 바뀌면 어댑터만 버전업. 서로의 숫자를 맞추지 않는다.
- **카탈로그 일관성**: 이 규칙으로 catalog에서 "v1.0 = 코어-어댑터 전환 완료"가 통일된 신호가 된다.
