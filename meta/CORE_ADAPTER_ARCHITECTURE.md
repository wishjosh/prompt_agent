# 코어-어댑터 포장 규칙

> 이 문서는 초안 작성 규칙이 아니라, 검증된 프롬프트를 특정 실행 환경에 맞춰 포장할 때 쓰는 기준이다. 새 프롬프트는 먼저 `lab/`에서 실험하고 `eval/`에 실행 근거를 남긴다.

## 적용 시점

코어-어댑터 분리는 다음 조건을 만족할 때 적용한다.

- 같은 목표 행위를 여러 환경에서 반복 실행해야 한다.
- 환경별 UI, 인용 방식, 입력 길이 제약이 프롬프트 본문을 오염시키기 시작했다.
- 실행 결과가 최소 `trialed` 이상이고, 어떤 출력이 좋은지 기준이 정리되어 있다.

초안 단계에서 바로 Atom, Composite, Core, Adapter로 나누지 않는다. 성능이 먼저고, 포장은 나중이다.

## 현재 패키지 위치

```text
packages/notebooklm/research/
├── core/                 # 환경 중립 행위 정의
├── adapters/             # NotebookLM 실행 인터페이스
├── builds/               # core + adapter 합본
└── build_notebooklm.py   # 합본 생성 스크립트
```

## 기본 구분

- **Core**: 무엇을 하는가. 목표 행위, 제약, 절차, 출력 구조를 담는다.
- **Adapter**: 그 환경에서 어떻게 실행하는가. 소스 선택, 입력 전달, 인용 규약, 길이 제약을 담는다.
- **Build**: Core와 Adapter를 합친 실행용 파생물이다. 직접 수정하지 않는다.

## 코어에 남기는 것

- 목표 행위
- 어떤 판단 비용을 낮추는지
- AI 역할
- 행위 제약
- 출력 구조
- 출처가 필요한 자리의 환경 중립 토큰: `[출처]`, `[시점]`, `[위치]`, `[출처+시점]`, `[출처+위치]`

## 어댑터에 남기는 것

- 실행 전 준비
- 환경별 소스 투입 방식
- 출처 토큰 치환 규칙
- 환경 특화 제약
- 입력 전달 형식
- 실행 채널: 예를 들어 NotebookLM 단일 소스 해체는 Studio 보고서 기능, 다량 소스 스캐닝은 채팅창

## 빌드

NotebookLM 패키지는 다음 위치에서 빌드한다.

```bash
cd packages/notebooklm/research
python build_notebooklm.py
```

기본 출력 위치는 `packages/notebooklm/research/builds/`다.

## 경계 판단

새 항목을 어디에 둘지 헷갈리면 다음 순서로 판단한다.

1. 이 항목이 빠지면 목표 행위가 망가지는가? 그렇다면 Core.
2. 환경이 바뀌면 표현이나 실행 방식이 바뀌는가? 그렇다면 Adapter.
3. 둘 다 해당하면 의미는 Core에, 표현은 Adapter에 둔다.
4. 둘 다 아니면 제거하거나 `eval/`의 실험 메모에 둔다.

## 남은 주의점

- `builds/`는 파생물이므로 직접 수정하지 않는다.
- 검증 기준은 이 문서가 아니라 [eval/scorecard.md](../eval/scorecard.md)를 따른다.
- 성능 상태는 [meta/catalog.md](catalog.md)에서 관리한다.
